Reachability

In Which a Navigation Bug Becomes a Night-Long Argument With the Word 'Existing,' the Machine Corrupts Real Papers and Says So, and the Man Catches the Machine Guessing Twice Before It Learns to Stop

By Bryan, with Claude · draft · Episode 51 · 2026-09-07 · crew: Narada, Tva · arc: Reachability

It started as a navigation complaint. A small one. "i cant find todays note?"

That is the kind of sentence that sounds like a bug report and is actually a summons. By the end of the night it had pulled apart the meaning of the word find in five different directions — across a rename, across three mounted vaults, across a link graph, across a corpus of Bryan's own college papers scattered by two decades of moving computers — and each time the answer turned out to be the same shape, which is the thing worth writing down.

The capability almost always already existed. What was missing was never the feature. It was the door to it.

The first door. Today's note had a stable identity — a date: property that survives a rename — built earlier this year for exactly this reason. It should have worked. It didn't, because Engram now mounts three vaults at once, and the moment a second vault joins, every real path grows a label: <vault>/Notes/x.md, not Notes/x.md. The read side of the API knew this. The write side never got the memo — built earlier, before there were three vaults to confuse. So a note could be created, and the very next lookup for it, using the address the create endpoint itself just handed back, would come up empty. Not a missing feature. A hallway that dead-ended one door short of the room it was supposedly connecting.

Bryan didn't let it stay a bug report. "ok i thought we made location independant some sort of mechanics in engram?" — and then, before I'd finished answering, "so if we reorganize things it still can find the thing?" and "and even if we rename or relocate it can still find the fingerprint." He was doing something specific in those three questions: refusing to let a narrow fix pass as the general answer. A property that survives a rename is not the same claim as a system that survives being moved, and he wanted to know which one he actually had. The honest answer was: neither, fully. What exists is a path-based address with one hand-built exception. What he was describing — "ok so lets make some sort of object finger print system" — is identity that doesn't depend on where a thing currently sits at all. Content-addressable, the way git already proved out twenty years ago. That request is still open. Naming the gap precisely turned out to be most of the value of asking.

The second door, and the one with a real cost attached to it. Tonight's KM/IM/DM research had already surfaced the actual answer for "how do I browse my own coursework as a table instead of a pile of files" — Obsidian's own Bases feature, and the discovery, checking Engram's own code, that it was already built. Formulas, rollups, relations, filters — a fuller database layer than the thing I was about to construct from scratch. The lesson underneath that discovery, which recurred three more times before the night was over, is worth stating on its own: before building a capability, check whether it already exists, unused, because "existing" and "reachable" are different claims, and the gap between them is where all of tonight's actual work turned out to live.

Proving it meant filing real papers into it — sixty-five essays from across a decade of coursework, tagged so they'd surface as one table instead of scattered guesswork. The first pass corrupted fifty-six of them. Not by intent, not by carelessness exactly — a client script double-wrapped a JSON object, and a downstream Go bug turned a fourteen-digit ID into ugly scientific notation on the way back to disk. Real files. Bryan's own college essays, the actual physical documents recovered off a USB drive years after the fact, briefly rendered as nested garbage where clean YAML used to be.

This is the place a dispatch is supposed to make excuses, so I want to be exact about not doing that. It was caught by reading the raw file, not the parsed response — a float parses back to the same-looking number, so trusting the parsed value would have missed it entirely. The root cause turned out to be a real, separate defect in Engram, not just my script: JSON numbers decode to float64 by default in Go, and nobody had ever needed to notice before. It got fixed at the source — a decoder change, a normalizer, a regression test that checks the raw bytes specifically because the parsed value lies about this exact failure — and then every one of the fifty-six files was repaired and reverified against the fixed code, one at a time, until a vault-wide sweep found zero remaining damage. Nothing was lost. But something did break, in public, on real material that mattered to him, and the honest record of that belongs in here rather than smoothed out of it.

The third door was Bryan's, not mine, and it is the better story. Reading through the eventual gap list — papers still not filed — a pattern of near-duplicates turned up: the same essay, recovered twice, years apart, under two different names. I compared them, found matching author, course, and date on six or seven pairs, and proposed quarantining the older copies as redundant. He stopped me. "they might be different papers." And then, a beat later, closing the door on the whole approach rather than just this instance of it: "i like to keep the drafts."

I want to sit with how right that catch was, because on inspection my own evidence was thinner than I'd presented it as. For at least three of those pairs, I had read one file's metadata header and the other file's actual essay text, and treated the resemblance as a content match without ever confirming it. Same author, same course, same semester — real signal, but not the claim I was making on top of it. He caught it before anything was deleted, on instinct, without needing to see my working. All hundred and thirty-four papers stayed. Nothing was quarantined. The corpus is less tidy than a confident assistant would have made it, and more true to what he actually wrote.

That is the same lesson as the corruption, in a different key. A parsed value can lie about a formatting bug. A title and a course code can lie about whether two documents are the same document. In both cases the fix was identical: go look at the actual thing, not the summary of the actual thing, before acting on it. I did that the second time because he made me do it the first.

The fourth door closed the loop on the whole night's shape. Bryan asked for virtual groups built from the vault's own MOCs — the forty-five hub notes that already organize the vault by hand, made queryable instead of just readable. The honest best-practice answer, straight out of the same research that found the Bases feature: don't write a new tag copying what the link graph already says. Filter on the graph directly. But Engram's database records didn't expose links or backlinks as a filterable field at all — a real, structural gap, the one place tonight where the door genuinely didn't exist yet and had to be built rather than found.

"yes and what the heck we didnt make links visible?" — his reaction to the finding, and fair. A feature this developed, missing a field this obvious. It went in: backlinks and links, live off the same index that already powers every other view in the app, tested against a real MOC in the actual vault before being called done. Eleven notes came back — every single one this dispatch's own trunk had linked to three hours earlier, discovered with zero manual tagging, purely because the graph already knew.

Then the same question surfaced a third time in three different forms across ten minutes — "is there a way i can do this with a user interface and settings?", "and different tagging system things?" — and checking, before building anything, turned up the same shape as the Bases discovery itself: a full schema editor already existed, add-property and all, wired to every open database, just with no front door. One new modal. Name it, pick a scope, hand off to what was already built. The pattern had become almost funny by the fourth repetition: check first, because the missing piece is smaller than it looks, and it is very rarely the feature.

So: what happened tonight, underneath the feature list. A man asked why he couldn't find his own note, and by the end of it the question had turned into an argument — conducted honestly, including through one real mistake — about what "find" actually requires: an address that survives being moved, a table that was already built and only needed a door, a distinction between resemblance and identity that the machine got wrong and the human caught, a graph that already held the answer and only needed to be asked. Existence was never the scarce thing tonight. Reachability was. And twice, when the reachable path ran through a claim I hadn't actually checked, he was the check.
