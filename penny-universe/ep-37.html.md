# Episode 37: The Validator

Bryan, with Claude · draft · Episode 37 · 2026-04-10 · crew: Tva, Durga · arc: Tools for real buildings

In Which a Proprietary Binary Format Gets Reverse-Engineered Over Lunch, a C# Inspector Learns to Read Wiring Diagrams Nobody Was Supposed to Read, and the First Validator for Niagara GFX Files Discovers That Every Building Has Ghosts in Its Graphics

## Chapter 1: The Format Nobody Documents

Niagara `.gfx` files are the graphical interfaces for building automation systems. Every HVAC control screen you've never noticed — the one showing your building's air handlers, boilers, chilled water loops, and alarm panels — is stored as a `.gfx` file on a JACE controller somewhere in a mechanical room.

Tridium, the vendor, provides a graphical editor called Workbench. You drag and drop widgets. You bind them to control points. You save. A `.gfx` file comes out.

What Tridium does not provide is documentation for what's inside that file.

This is not unusual in building automation. The industry runs on proprietary formats, vendor lock-in, and the assumption that nobody will ever need to read the files programmatically. You use the vendor tool or you don't. There is no third option.

Bryan has maintained a campus of buildings for years. He has opinions about this.

## Chapter 2: The Archive

A `.gfx` file is a ZIP archive. That's the first thing the inspector learned.

Inside the ZIP: `Main.xml` (the actual graphics document), `Info/ProjectInfo.xml` (metadata), `Info/InternalPoints.xml` (point bindings), and sometimes additional resources. All XML. All undocumented. All interconnected in ways that the Workbench editor hides behind a drag-and-drop interface.

The C# inspector — built in an afternoon as a console application — starts by opening the archive and checking for required entries. If `Main.xml` is missing, the file is corrupt or not actually a `.gfx`. If `ProjectInfo.xml` is missing, you can't identify what building or system the graphic belongs to.

Then it reads `Main.xml` and starts mapping.

## Chapter 3: The Namespace Map

Every widget in a `.gfx` file has a type. Types live in namespaces. The namespace block at the top of `Main.xml` declares which widget libraries the graphic uses — `kitPx` for pixel-based widgets, `gx` for core graphics primitives, `kitChart` for trend charts, `web` for browser integration.

The inspector extracts the full namespace map. Eleven entries in the test file. Each one is a module from the Niagara framework — a dependency that must be present on the JACE controller for the graphic to render.

This is information that Workbench users never see. They see widgets. They don't see dependencies. When a graphic fails to load on a controller, the first question is always "which modules are missing?" The namespace map answers that question before you even open Workbench.

## Chapter 4: The Wiring

Graphics aren't just pictures. They're wired.

Every widget has an `id` — a unique registration in the document. Other widgets can reference that `id` via `ref` attributes (single references) or `refs` attributes (collection references). The wiring creates a graph: this label displays the value from that point. This animation triggers when that alarm fires. This button navigates to that page.

The inspector counts everything:

- How many `id` registrations
- How many `ref` references
- How many `refs` collection references
- Which `ref` values point to `id` values that don't exist (orphan references)
- Which `id` registrations are self-closing tags with no content (likely null registrations — they reserve a name but do nothing)

Orphan references are ghosts. They point to widgets that were deleted, renamed, or never existed. In a vendor tool, you can't see them. The graphic renders, the orphan reference silently fails, and nobody knows there's a broken wire until something stops updating and a building manager calls at 2 AM.

The first real `.gfx` file had orphan references. Of course it did. Every building has ghosts in its graphics.

## Chapter 5: The Collection Families

The deepest layer: `ShapeCollection` objects.

A `ShapeCollection` is a container widget that holds other widgets in an ordered list. The list items reference child widgets by `id`. But some referenced items aren't shapes — they're `Link` objects, which are invisible wiring connections, not visible graphics.

The inspector detects `Link` objects inside `ShapeCollection` item lists. This is a graph-aware check. It requires understanding not just the XML structure but the semantic meaning of the node types.

A `Link` in a `ShapeCollection` isn't wrong, exactly. But it's suspicious. It means someone wired a data connection inside a visual container, which usually means the graphic was edited hastily, or a copy-paste brought invisible dependencies along for the ride.

This is the kind of thing that Tridium's own tools don't flag. Not because they can't — because they don't think it's important. Bryan thinks it's important because Bryan is the person who gets called when the graphic breaks.

## Chapter 6: First Blood

The inspector ran against a real `.gfx` file exported from a live JACE controller. A heating loop graphic from one of Bryan's buildings.

Results:

- Archive opened cleanly
- Required entries present
- Namespace map: 11 entries
- ID registrations: counted
- Ref/refs counted
- Orphan references: found
- Self-closing ID warnings: found
- Collection-family anomalies: detected

No documentation was consulted in the making of this tool. Because none exists.

The building automation industry has been generating these files for twenty years. Nobody has built a standalone validator before. Not because it's impossible — the format is just XML in a ZIP — but because nobody at the vendor level thinks technicians need to read the wiring.

Bryan disagrees. Bryan built a tool. The tool found ghosts.

Durga would approve. She always said: trust nothing, verify everything. The validator is just Durga's philosophy applied to `.gfx` files.

Security isn't always about attackers. Sometimes it's about seeing what's actually there.
